# Idle Warehouse Dashboard Slice Contract

## Overview

DashForge operates as an internal consulting delivery accelerator for Anblicks, designed to empower client delivery leads, consultants, and practice directors to present credible, interactive, and industry-specific dashboard experiences during executive workshops. Rather than relying on static slides, abstract wireframes, or empty BI tool canvases, DashForge delivers fully functional client-side dashboard experiences that prove immediate consulting value.

The `idle-warehouse-dashboard` vertical slice establishes the buyer-visible frontend presentation layer for the Idle Warehouse Waste cost accelerator, targeting chief information officers (CIOs), chief technology officers (CTOs), and FinOps practice leaders. This slice consumes the existing `idle-warehouse-waste` backend slice and presents actionable cloud data warehouse cost metrics, resource waste patterns, and prioritized, owner-validated recommendations using TVIQ-shaped (Time-to-Value, Impact, Quality) data structures. The slice focuses strictly on the browser-based presentation tier without altering the underlying data generation, relational extraction, or schema definition layers. By proving the end-to-end user experience in a zero-dependency standalone production build served directly in the browser, DashForge enables Anblicks consultants to deliver authoritative pre-sales discovery demonstrations and executive follow-up deliverables completely offline, establishing consulting credibility from day one.

## Problem

Enterprise analytics leaders and FinOps executives are under intense executive pressure to identify and remediate cloud infrastructure spend inefficiencies, particularly Snowflake compute waste caused by unmonitored idle warehouses, missing resource monitors, and excessive auto-suspend timeouts. However, consulting teams attempting to demonstrate optimization capabilities face significant pre-sales roadblocks. Connecting directly to a prospective client's production Snowflake environment during early discovery conversations is almost always prohibited by enterprise security, governance, compliance, and procurement policies. Conversely, presenting generic slide decks or static mockups lacks analytical credibility and fails to engage technical decision-makers.

Consultants require an interactive, standalone browser dashboard that looks and behaves like an enterprise-grade cloud cost management application. The dashboard must immediately convey the scale of waste—such as headline credit opportunity figures and compute credit concentration in unmanaged workloads like `FINANCE_REPORTING_WH`—while providing a governed, prioritized recommendation queue that displays suggested owners, specific remediation actions, evidence details, and safety guardrails. Crucially, the solution must operate in a self-contained browser runtime without requiring an active backend or live credentials, must never hide or suppress its synthetic demo data provenance, and must preserve existing core features, templates, and industry packs across DashForge without architectural drift or regressions.

## Required Outputs

This slice governs the definition, authoring, and verification of the following core deliverables across the implementation lifecycle:

- `docs/idle-warehouse-dashboard-contract.md`: The formal slice contract articulating the problem statement, system constraints, required outputs, multi-tier validation strategy, execution routing intent, and enumerated acceptance checks (`AC-1` through `AC-8`).
- `journeys/user_journeys_manifest.json`: The synchronized user journeys manifest mapping natural-language operator journeys to every acceptance check (`AC-1` through `AC-8`), establishing verifiable command chains, non-empty command allowlists, and execution authorities.
- Standalone Dashboard Presentation Layer (`frontend/src/features/runtime/StandaloneDashboardApp.tsx`, `standaloneDashboard.ts`, `idleWarehousePresentation.ts`): The browser-visible React application implementing URL scenario resolution, controlled readiness state management, synthetic disclosures, recommendation queue interactions, and executive follow-up exports.
- Scenario Blueprint and Preview Bundles (`scenarios/idle-warehouse-waste/`): Packaged scenario specification, preview data, and blueprint assets enabling the standalone frontend build to load the scenario seamlessly via `StaticDataAdapter` and `DashboardSpec` runtime seams.
- Browser Smoke Gate Manifest and Conformance (`tests/browser_smoke_manifest.json`, `tests/browser_smoke_check.py`): Pinned browser smoke manifest validating production bundle serving, DOM readiness, disclosure visibility, and interactive recommendation queue expansion.
- Automated Test Suites: Comprehensive frontend tests (`frontend/src/features/runtime/StandaloneDashboardApp.test.tsx`) covering scenario routing, readiness, disclosures, and recommendation queues; and regression pytest suites (`tests/test_idle_warehouse_waste.py`) ensuring full backwards compatibility.

## Constraints

The implementation, verification, and execution of the `idle-warehouse-dashboard` slice are governed by the following strict architectural and operational constraints:

1. **Frontend-Focused Presentation Scope**: The slice focuses strictly on the browser-based presentation layer. It must not alter the underlying data generation, relational schema definitions, or extraction algorithms in `src/dashForge/` or sibling project `dataForge/`. All backend components delivered in previous slices remain authoritative.
2. **Zero Live Infrastructure Dependencies**: The dashboard must run entirely standalone in the browser without live Snowflake connections, external database servers, API gateways, or external cloud networks. All data must resolve locally through `StaticDataAdapter` and canonical `DashboardSpec` contracts.
3. **No Secondary Renderers or Engines**: Presentational views must consume data exclusively through the existing `DashboardSpec` -> `DataAdapter` -> `DashboardRenderer` pipeline. Introducing ad-hoc charting libraries, secondary rendering paths, or independent recommendation engines is strictly prohibited.
4. **Governed Recommendation Safety and Framing**: All recommendations displayed in the queue must preserve governance fields (`executive_severity`, `suggested_owner`, `recommended_action`, `evidence_detail`, `guardrail`) and explicitly frame savings as directional until validated by designated warehouse owners, preventing ungrounded or destructive automated changes.
5. **Persistent and Unsuppressed Synthetic Disclosure**: A visible disclosure bearing `data-disclosure="synthetic-demo-data"` and the exact text `"Synthetic demo data"` must remain prominent across all dashboard views and exported buyer deliverables. Suppressing, hiding, or obscuring this disclosure is forbidden.
6. **Strict Browser Smoke Gate Alignment**: The production build served from `frontend/dist` must conform exactly to the selectors, interactions, and text assertions pinned in `tests/browser_smoke_manifest.json` without modifying the pinned manifest.
7. **Production Build Integrity**: The slice must build cleanly via `npm --prefix frontend run build` (or `npm --prefix frontend ci && npm --prefix frontend run build`), producing `frontend/dist/index.html` and bundled assets with zero TypeScript compilation errors or linter violations.
8. **Preserved Test Suite and Verbatim Execution**: All allowlisted commands and journey commands must run verbatim from the workspace root. Python test execution must be exactly `python3 -m pytest tests/ -q` with NO PYTHONPATH override. Application CLI commands must use the `env PYTHONPATH=src` prefix.
9. **Governed Write Scope Enforcement**: Persisted file writes for this step are strictly restricted to the `docs/` and `journeys/` directories. Modifying any file outside these designated directories causes immediate step failure under Agent-Orch governance.

## Validation

Verification of the `idle-warehouse-dashboard` slice follows a multi-tier deterministic validation protocol:

1. **Automated Frontend Test Suite**: Execution of `npm --prefix frontend test -- --run` to verify that all 35 test files and 108+ unit and integration tests pass cleanly, confirming proper behavior for scenario selection, readiness transitions, synthetic disclosures, recommendation queue interactions, and PDF export workflows.
2. **Production Build Verification**: Execution of `npm --prefix frontend run build` to confirm clean TypeScript compilation across `tsconfig.app.json`, `tsconfig.node.json`, and `tsconfig.package-tools.json`, producing optimized production bundles in `frontend/dist/` including `dist/index.html`.
3. **Browser Smoke Gate Conformance**: Verification via `tests/browser_smoke_manifest.json` that when the production build is served locally, the standalone application responds at `http://127.0.0.1:4173/?scenario=idle-warehouse-waste`, matches the ready selector `[data-scenario='idle-warehouse-waste'][data-readiness='controlled'] [data-disclosure='synthetic-demo-data']`, successfully processes the click action on `[data-action='open-recommendation-queue']`, and renders the recommendation queue with `FINANCE_REPORTING_WH`.
4. **Contract Marker Inspection**: Verification via `tests/browser_smoke_check.py` that the compiled production bundle contains the required contract marker strings: `"idle-warehouse-waste"`, `"synthetic-demo-data"`, `"open-recommendation-queue"`, and `"recommendation-queue"`.
5. **Full Python Test Suite Regression**: Execution of `python3 -m pytest tests/ -q` with NO PYTHONPATH override to confirm that all 112 Python unit and integration tests pass cleanly, ensuring that backend packaging, fail-closed CLI behaviors, and existing industry packs (`healthcare`, `financial`, `saas`) suffer no regressions.
6. **User Journey Simulation Verification**: Execution of synchronized user journeys in `journeys/user_journeys_manifest.json` through the Agent-Orch simulation harness, verifying that all commands match allowlisted prefixes and succeed with expected exit statuses and outputs.

## Routing Intent

Execution routing across the governed slice lifecycle is structured as follows:

- **Producer / Contract Author Route (`antigravity_cli` / `gemini-3.8-flash-high`)**: Establishes the formal slice contract in `docs/idle-warehouse-dashboard-contract.md` and synchronizes the user journeys manifest in `journeys/user_journeys_manifest.json` within allowed paths (`docs/`, `journeys/`).
- **Planner Route (`antigravity_cli` / `gemini-3.8-flash-high`)**: Formulates the implementation and verification plan under `plans/`, establishing explicit traceability between acceptance checks, frontend modules, build targets, and verification steps.
- **Test Author Route (`antigravity_cli` / `gemini-3.8-flash-high`)**: Validates and enhances frontend and integration tests in `frontend/src/features/runtime/StandaloneDashboardApp.test.tsx` and Python test companions prior to full implementation closure.
- **Implementation Route (`antigravity_cli` / `gemini-3.8-flash-high`)**: Implements frontend presentation components, asset bundles, and build configurations to satisfy all acceptance checks.
- **Evaluator / User Tester Route (`user_tester` / `gemini-3.1-pro`)**: Re-executes allowlisted user journey commands from the workspace root against the synchronized manifest, validating claimed outputs and exit codes without performing code modifications.
- **Independent Reviewer Route (`slice_reviewer` / `gemini-3.1-pro`)**: Performs a read-only audit of implementation diffs, build artifacts, test execution logs, and contract traceability to render an authoritative review verdict.

## Acceptance Checks

The `idle-warehouse-dashboard` vertical slice must satisfy the following explicit acceptance checks:

- **AC-1**: The standalone frontend application served from `frontend/dist` mounts at `/?scenario=idle-warehouse-waste` without requiring live Snowflake credentials, an active backend server, or manual dataForge receipt orchestration, loading the scenario snapshot assets through canonical `StaticDataAdapter` and `DashboardSpec` seams while preventing duplicate rendering pipelines or secondary query engines.
- **AC-2**: The scenario container element in the DOM carries explicit `data-scenario="idle-warehouse-waste"` and transitions to `data-readiness="controlled"` upon successful resolution of the verified scenario snapshot data and claim ledger, providing unambiguous readiness signals for automated browser smoke runners and human operators.
- **AC-3**: The dashboard renders a persistent, unsuppressed disclosure element bearing `data-disclosure="synthetic-demo-data"` and displaying the exact text `"Synthetic demo data"`, with the disclosure prominently visible across all executive dashboard views and faithfully preserved in generated downstream buyer deliverables, including print-to-PDF views and executive follow-up exports.
- **AC-4**: The user interface provides an accessible interactive control with `data-action="open-recommendation-queue"` that toggles the prioritized recommendation queue; when opened, the container carries `data-status="recommendation-queue"` and displays prioritized recommendations derived from the `recommendation_queue` dataset, listing `FINANCE_REPORTING_WH` (`IWW-001`, Priority `P0`) first and displaying `executive_severity`, `suggested_owner`, `recommended_action`, `evidence_detail`, and protective safety `guardrail` terms that explicitly frame savings as directional until validated by designated warehouse owners.
- **AC-5**: The dashboard integrates the existing `data-action="same-day-executive-follow-up"` control and landscape PDF export capability (`data-testid="dashboard-save-pdf"`) directly into the idle warehouse workflow without duplicating artifact generation logic, ensuring exported artifacts preserve the scenario narrative, headline opportunity metrics, verified artifact digest citations, and required `"Synthetic demo data"` disclosures.
- **AC-6**: The production build served at `http://127.0.0.1:4173/?scenario=idle-warehouse-waste` satisfies the exact contract verified by `tests/browser_smoke_manifest.json` and `tests/browser_smoke_check.py`, ensuring that the HTML `#root` mount element is present and the compiled JavaScript production bundles under `frontend/dist/assets/` contain the essential contract marker strings: `"idle-warehouse-waste"`, `"synthetic-demo-data"`, `"open-recommendation-queue"`, and `"recommendation-queue"`.
- **AC-7**: The frontend build pipeline (`npm --prefix frontend run build`) executes cleanly to compile TypeScript and bundle static production assets into `frontend/dist/index.html` and supporting bundles, while the automated frontend test suite executes green without errors or skipped assertions via `npm --prefix frontend test -- --run` across all test files.
- **AC-8**: The frontend dashboard consumes data strictly as shaped by the existing `idle-warehouse-waste` backend slice without modifying underlying data generation, extraction, or relational schema layers in Python or sibling project `dataForge/`; all existing CLI commands (`env PYTHONPATH=src python3 -m dashForge.main generate`), existing industry packs (`healthcare`, `financial`, `saas`), and the full automated Python test suite (`python3 -m pytest tests/ -q` with NO PYTHONPATH override) pass cleanly without regression.
