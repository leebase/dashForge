# Cost Management Storage Waste Slice Contract

## Overview

DashForge operates as an internal enterprise consulting delivery accelerator for Anblicks, designed to empower practice directors, cloud architects, FinOps practitioners, and client delivery leads to conduct high-impact, credible executive discovery workshops. Rather than relying on conceptual wireframes, static slide decks, or empty business intelligence canvases that create weeks of misaligned rework, DashForge delivers fully functional, standalone client-side dashboard experiences that prove immediate consulting value completely offline without requiring live cloud credentials or external network connectivity.

The `cost-management-storage-waste` vertical slice establishes the buyer-facing Storage Waste dashboard experience for the Snowflake Cost Management accelerator (`snowflakeCost:storage-waste`). While compute warehouse optimization addresses active processing spend, storage costs in enterprise cloud data warehouses represent a persistent, compounding, and frequently unscrutinized budget drain. Enterprise Snowflake tenants regularly accumulate terabytes to petabytes of stale, unqueried tables, orphaned intermediate staging objects, and uncompressed storage tiers that quietly inflate monthly invoices.

This slice delivers an authoritative, interactive presentation layer engineered for executive buyers—specifically Chief Financial Officers (CFOs), Chief Information Officers (CIOs), VPs of Enterprise Data, and FinOps practice leaders. The slice ingests deterministic dataForge exports as a provenance-labeled snapshot conforming to canonical contracts, maps storage waste telemetry across standard `DashboardSpec` and `DataAdapter` runtime seams, surfaces prioritized recommendations for stale tables and uncompressed storage with all six governance attributes, and provides same-day follow-up deliverables. Existing DashForge behavior, templates, and accelerator slices (`healthcare`, `financial`, `saas`, `snowflakeCost:idle-warehouse-waste`, `snowflakeRbac:rbac-audit-foundation`) remain completely intact and unmodified.

## Problem

Enterprise organizations migrating to or operating on cloud data platforms like Snowflake frequently suffer from storage bloat and lack of lifecycle hygiene. Unlike compute warehouses where cost spikes trigger immediate operational alarms, storage costs accumulate silently over quarters and years. Development tables cloned for one-off testing, historical staging tables from deprecated ETL/ELT pipelines, and intermediate analytical datasets remain active on billable storage indefinitely without active query workload. Furthermore, tables ingested or loaded using suboptimal compression formats or staging policies consume substantially more billable byte-hours than properly compressed columnar storage.

During executive pre-sales and architectural discovery workshops, Anblicks consulting teams face a pervasive delivery dilemma. Prospective enterprise buyers cannot furnish live production Snowflake credentials to third-party consultants due to strict information security policies, regulatory compliance constraints (such as SOC 2, HIPAA, and GDPR), and corporate procurement restrictions that take weeks or months to navigate. Conversely, generic static mockups, abstract slide decks, or toy dummy spreadsheets fail to demonstrate the analytical depth and FinOps rigor required to convince technical and financial buyers of Anblicks' expertise.

To break this pre-sales impasse, DashForge requires a dedicated, buyer-facing Storage Waste dashboard slice. This slice must ingest deterministic, relational Snowflake storage telemetry from sibling project `dataForge` as a read-only, provenance-labeled snapshot; present clear headline recoverable savings metrics; categorize storage waste into actionable dimensions such as stale table retention and uncompressed storage overhead; deliver a prioritized recommendation queue with explicit governance guardrails; and operate entirely offline with zero backend servers, zero live credentials, and zero cloud network dependencies.

## Constraints

The implementation, execution, and verification of the `cost-management-storage-waste` vertical slice are strictly governed by the following architectural, operational, and governance constraints:

1. **Preservation of Existing DashForge Components & Zero Fragmentation**: All existing industry packs (`healthcare`, `financial`, `saas`, and `snowflakeCost:idle-warehouse-waste`, `snowflakeRbac:rbac-audit-foundation`), CLI generate entrypoints, template catalogs, and dashboard presentation surfaces must remain intact without fragmentation or regressions.
2. **Read-Only dataForge Boundary & Sibling Project Isolation**: Sibling project `dataForge` remains strictly read-only. No files within `dataForge/` may be added, modified, or deleted during contract definition, planning, implementation, or verification.
3. **Canonical Snapshot Conformance**: Storage waste scenario exports must strictly adhere to the canonical `SQLiteSnapshot` TypeScript contract (`frontend/src/core/data/sqliteSnapshot.ts`) generated via `src/dashForge/package_snapshot.py`. No bespoke or secondary snapshot serialization formats may be introduced.
4. **Provenance Tracking and Synthetic Disclosure Integrity**: Exported snapshot artifacts and presentation views must carry complete provenance metadata (`packId: "snowflakeCost"`, `scenarioId: "storage-waste"`, seed, generator version, ISO-8601 timestamp, `synthetic: true`, and disclosure text `"Synthetic demo data"`). Synthetic disclosures must remain prominent, unsuppressed, and visible across all UI views and exported deliverables.
5. **Decoupled Architecture & Zero Live Dependencies**: The storage waste dashboard runs entirely client-side in-browser without live Snowflake database connections, external cloud credentials, backend servers, or external network requests. All data must resolve locally through canonical `DataAdapter` interfaces (`StaticDataAdapter`, `SyntheticDataArtifactAdapter`, `SQLiteDataAdapter`).
6. **Canonical Runtime Seams & DataAdapter Interfaces**: Presentation widgets and components consume data strictly through canonical `DashboardSpec` contracts and `DataAdapter` query interfaces without introducing secondary renderers, ad-hoc charting libraries, or independent query engines.
7. **Governed Recommendation Queue & Directional Owner Guardrails**: Recommendations presented to users must be derived directly from the `recommendation_queue` dataset, preserving all six governance fields (`recommendation_id`, `executive_severity`, `suggested_owner`, `recommended_action`, `evidence_detail`, and `guardrail`). All projected savings and table lifecycle remediations must be explicitly framed as directional until confirmed by designated data owners and stewards. Destructive table drops or automated data purging without human stakeholder authorization are strictly prohibited.
8. **Fail-Closed CLI Behavior & Overwrite Guard**: The CLI command `env PYTHONPATH=src python3 -m dashForge.main generate` must fail closed with exit status 2 and clean diagnostic messages via `parser.error()` when required parameters are missing, invalid scenarios are supplied, or target output paths exist without the explicit `--force` flag.
9. **Verbatim Direct Argv Workspace-Root Execution**: All commands declared in `command_allowlist` and journeys must execute verbatim from workspace root using direct subprocess invocation (`shell=False`). Application commands must use `env PYTHONPATH=src python3 -m dashForge.main`. Test suite commands must use `python3 -m pytest tests/ -q` with NO `PYTHONPATH` override. Browser tests use `npm --prefix frontend test -- --run`. Shell operators (`|`, `&&`, `||`, `;`, `<`, `>`) and standalone shell tools (`jq`, `grep`, `cat`) are strictly prohibited as sole journey verification evidence.
10. **Browser Smoke Gate Conformance**: Production builds compiled via `npm --prefix frontend run build` must compile cleanly with zero TypeScript errors, preserving required contract markers for browser smoke testing. The local server start command recorded in `tests/browser_smoke_manifest.json` is not a re-executable journey claim and must not be allowlisted or recorded as a journey's only evidence.
11. **Governed Write Scope Enforcement**: Persisted file modifications for this step are strictly restricted to `docs/` and `journeys/`. Modifying any path outside these boundaries results in immediate step failure under Agent-Orch governance.
