# Synthetic RBAC Audit Foundation Slice Contract

## Overview

DashForge operates as an internal enterprise consulting delivery accelerator for Anblicks, empowering practice directors, cybersecurity architects, client delivery leads, and data engineering consultants to conduct high-impact, credible executive discovery workshops. Rather than demonstrating technical vision through abstract slide decks, conceptual wireframes, or empty business intelligence shells, DashForge delivers fully functional, standalone client-side dashboard experiences that prove immediate consulting value completely offline and without requiring live cloud credentials or external network connectivity.

The `synthetic-rbac-audit-foundation` vertical slice establishes the foundational synthetic data models and dashboard specification for the RBAC (Role-Based Access Control) management accelerator in DashForge (`snowflakeRbac:rbac-audit-foundation`). In enterprise cloud data warehouses such as Snowflake, access control management is notoriously fraught with complexity: opaque multi-tier role inheritance, unmonitored privilege escalation paths, dormant user accounts with administrative entitlements, and a lack of consolidated visibility into securable object grants. Prospective enterprise buyers—specifically Chief Information Security Officers (CISOs), Cloud Security Architects, Data Governance Directors, and Snowflake Administrators—routinely struggle to audit and govern these permissions. However, pre-sales consultants cannot access prospective clients' live production environments due to infosec barriers and data privacy compliance restrictions.

This slice directly addresses that critical consulting delivery impasse. By formalizing realistic, relational synthetic access control telemetry and an interactive dashboard specification, this slice enables prospective buyers to visualize their role hierarchies and audit user access without requiring live Snowflake data, turning a pervasive administrative pain point into a structured, governed data story. Existing DashForge industry packs (`healthcare`, `financial`, `saas`, `snowflakeCost`) and sibling project `dataForge` components remain strictly intact and isolated without fragmentation or regressions.

## Problem

Enterprise cloud data platforms require rigorous security and governance controls, yet Role-Based Access Control in Snowflake frequently degrades into an unmanageable web of permissions over time. Organizations accumulate hundreds of custom roles, circular grant relationships, redundant role hierarchies, and orphaned user accounts. Security administrators and audit teams struggle to answer fundamental compliance questions: Which users possess indirect administrative access through nested role inheritance? Which service accounts or dormant users retain `ACCOUNTADMIN` or `SECURITYADMIN` privileges? What sensitive databases, schemas, or compute warehouses are exposed to broad functional roles?

During enterprise discovery and pre-sales workshops, Anblicks consultants face a formidable obstacle. Prospective buyers cannot furnish live production Snowflake credentials to third-party consultants due to strict information security policies, regulatory compliance constraints (such as SOC 2, HIPAA, and GDPR), and complex vendor onboarding reviews that take weeks or months to finalize. Conversely, generic static mockups, abstract identity governance slides, or toy datasets with flat dummy rows fail to demonstrate the sophisticated graph depth and analytical rigor required to convince security leaders of Anblicks' delivery expertise.

To break this pre-sales deadlock, DashForge requires a dedicated foundational vertical slice for the RBAC management accelerator. This slice must define rich synthetic data models capturing realistic role hierarchies, user-to-role grants, securable object permissions, and prioritized governance findings. Furthermore, it must define the formal `DashboardSpec` specification establishing KPI scorecards, interactive role hierarchy graph visualization, user access audit matrices, and risk queues that bind seamlessly to DashForge's canonical `DataAdapter` seams. Delivering this capability enables consulting teams to walk into executive security discovery sessions and immediately demonstrate authoritative governance insights without external dependencies, live credentials, or post-meeting friction.

This slice governs the definition, authoring, and verification of the following formal deliverables:

- `docs/synthetic-rbac-audit-foundation-contract.md`: The authoritative slice contract defining the problem statement, required outputs, operational constraints, multi-tier validation methodology, execution routing intent, and enumerated acceptance checks (`AC-1` through `AC-6`) with at least 120 non-whitespace characters under each required heading.
- `journeys/user_journeys_manifest.json`: The synchronized user journeys manifest adhering strictly to `USER_JOURNEYS_MANIFEST_SCHEMA`, defining natural-language operator journeys that comprehensively trace to every acceptance check (`AC-1` through `AC-6`), declaring valid authorities (`human`, `mission`, `author`), and specifying an allowlist of verbatim executable commands runnable directly from the workspace root.
- Foundational Synthetic RBAC Relational Schema Contracts: Formal schema definitions across six canonical relational datasets: `rbac_summary` (headline access metrics: total roles, active users, elevated admin accounts, critical risk findings), `roles` (role definitions, types, owners, comments), `role_hierarchy` (parent-child inheritance links and tree depth), `user_role_assignments` (user identities, assigned roles, grant dates, MFA status, account activity status), `object_grants` (privilege grants on warehouses, databases, schemas, tables), and `governance_findings` (governed audit findings preserving all six canonical governance fields: `finding_id`, `executive_severity`, `suggested_owner`, `recommended_action`, `risk_detail`, and protective `guardrail`).
- RBAC Dashboard Specification (`DashboardSpec`): Standardized JSON dashboard specification declaring grid layout, KPI metric cards (Total Roles, Active Users, Elevated Admins, High-Risk Findings), role hierarchy tree visualization, user access audit matrix, and prioritized governance findings queue, binding to DashForge's standard `DataAdapter` runtime interfaces without bespoke or secondary renderers.
- Persistent Disclosures and Directional Security Guardrails: Comprehensive presentation and export structures featuring unsuppressed `data-disclosure="synthetic-demo-data"` elements with the exact text `"Synthetic demo data"`, accompanied by upstream provenance metadata and explicit directional validation notices stating that all access remediation recommendations are directional pending validation by designated security administrators.
- Automated Test Suites: Comprehensive Python regression tests (`tests/test_idle_warehouse_waste.py`, `tests/test_idle_warehouse_dashboard.py`, `tests/test_remediation_artifacts.py`, `tests/test_playbook_schema.py`) and frontend component tests (`npm --prefix frontend test -- --run -t "StandaloneDashboardApp"`) confirming schema adherence, CLI direct argv execution, browser build compatibility, and zero regressions across existing packages.

## Constraints

The implementation, verification, and operational governance of the `synthetic-rbac-audit-foundation` slice are strictly governed by the following operational constraints:

1. **Preservation of Existing dashForge Components & Zero Fragmentation**: All existing industry packs (`healthcare`, `financial`, `saas`, and `snowflakeCost:idle-warehouse-waste`), generators, CLI entrypoints, templates, and dashboard surfaces must remain intact without fragmentation or regressions.
2. **Read-Only dataForge Boundary & Sibling Project Isolation**: Sibling project `dataForge` remains strictly read-only. No files under `dataForge/` may be created, edited, or deleted.
3. **Decoupled Architecture & Zero Live Dependencies**: The RBAC management accelerator runs entirely client-side in-browser without live Snowflake database connections, cloud API credentials, or backend server dependencies. All data must resolve locally through `StaticDataAdapter`, `SyntheticDataArtifactAdapter`, or `SQLiteDataAdapter` contracts.
4. **Canonical Runtime Seams & DataAdapter Interfaces**: Presentation widgets and components consume data strictly through canonical `DashboardSpec` contracts and `DataAdapter` query interfaces (`StaticDataAdapter`, `SyntheticDataArtifactAdapter`, `SQLiteDataAdapter`) without bespoke or secondary renderers.
5. **Governed Access Findings & Directional Security Guardrails**: Governance findings must preserve all required governance fields (`finding_id`, `executive_severity`, `suggested_owner`, `recommended_action`, `risk_detail`, `guardrail`). All projected remediations and role revocation guidance must be explicitly framed as directional pending confirmation with designated security owners. Automated or destructive privilege revocations are strictly forbidden.
6. **Persistent & Unsuppressed Synthetic Data Disclosures**: Every presentation surface, view, and export deliverable must prominently feature `data-disclosure="synthetic-demo-data"` with the exact text `"Synthetic demo data"` and provenance metadata (`packId`, `scenarioId`, `seed`, `synthetic: true`, ISO-8601 timestamp), preventing synthetic workshop demonstrations from being misrepresented as audited production telemetry.
7. **Verbatim Workspace-Root Direct Argv Execution**: All commands declared in `command_allowlist` and journeys must execute verbatim from workspace root using direct argv subprocess execution (`shell=False`). Application commands must use `env PYTHONPATH=src python3 -m dashForge.main`. Test suite commands must use `python3 -m pytest tests/ -q` with NO `PYTHONPATH` override. Browser tests use `npm --prefix frontend test -- --run`. Shell operators (`|`, `&&`, `||`, `;`, `<`, `>`) and standalone utilities (`jq`, `grep`, `cat`) are prohibited as sole journey evidence.
8. **Browser Smoke Gate Conformance**: Production builds compiled via `npm --prefix frontend run build` must compile cleanly with zero TypeScript errors, preserving required contract markers for browser smoke testing. The local server start command recorded in `tests/browser_smoke_manifest.json` is not a re-executable journey claim and must not be allowlisted or recorded as a journey's only evidence.
9. **Governed Write Scope Enforcement**: Persisted file modifications for this step are strictly restricted to `docs/` and `journeys/`. Modifying any path outside these boundaries results in immediate step failure under Agent-Orch governance.
