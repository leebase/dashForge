# Repair Timeout Cascade Slice Contract

## Overview

DashForge operates as an internal Anblicks consulting accelerator engineered to deliver rapid, credible, and interactive dashboard experiences for enterprise client discovery workshops. Under the project's decoupled architecture, sibling project `dataForge` provides deterministic mock data generation, relational modeling, and synthetic data quality assurance, while DashForge owns scenario definitions, `DashboardSpec` schemas, `DataAdapter` runtime interfaces, and standalone presentation deliverables. Governed delivery workflows in DashForge are executed and validated under Agent-Orch, ensuring strict isolation, auditable verification trails, and reproducible execution artifacts across multi-step development lifecycles.

The `repair-timeout-cascade` slice addresses a critical stability and orchestration failure mode in governed runs: the recurring 600-second worker timeout cascade. In multi-step delivery pipelines, monolithic execution steps that bundle extensive tasks—such as full test suite runs, relational dataset generation, schema validation, and multi-file code authoring—frequently bump against or exceed the default 600-second execution window enforced by Agent-Orch worker adapters (such as `codex_cli`). When a monolithic step times out, the orchestrator terminates the worker and triggers automatic retry attempts. Because the retries attempt to execute the exact same undifferentiated monolithic scope from scratch without diagnostic visibility into intermediate progress or execution bottlenecks, subsequent attempts repeatedly exhaust the 600-second budget. This creates a timeout cascade that blocks workflow progression, wastes execution cycles, and halts governed delivery.

To permanently overcome this failure mode, this slice implements playbook deconstruction and structured diagnostic logging. Monolithic steps are broken down into discrete, bounded stages with explicit intermediate checkpoints and fine-grained time boundaries. Concurrently, lightweight, low-overhead diagnostic timing instrumentation is introduced across generation and packaging execution paths to safely identify performance bottlenecks in governed runs without altering core product behavior, corrupting payload streams, or breaking existing workflows.

## Problem

Agent-Orch governed delivery workflows in DashForge rely on strict per-step execution timeouts (defaulting to 600 seconds) to ensure that unattended worker processes do not stall indefinitely. While this safeguard is essential for pipeline health, it creates severe cascading failure dynamics when applied to monolithic workflow definitions:

1. **Monolithic Step Bundling**: Governing multi-step sprints or complex feature additions through single monolithic steps aggregates disparate operations—scenario loading, database generation, snapshot extraction, validation checks, and regression testing—into a single execution unit. When unforeseen delays occur (such as disk I/O latency, heavy test suites, or large synthetic table generation), the step exceeds the 600-second limit.
2. **Cascading Retries and Wasted Work**: Upon reaching the 600-second timeout, the orchestrator forcibly terminates the step and initiates a retry attempt. Because intermediate progress is uncheckpointed and unsealed, the retry repeats the entire workload from zero. Without architectural separation, the retry hits the exact same timeout boundary, creating a deterministic failure cascade that drains compute budgets and halts pipeline automation.
3. **Diagnostic Invisibility and Blind Troubleshooting**: Standard CLI generation and packaging operations output only terminal success summaries or raw exit codes. When a run experiences significant latency or stalls near the 600-second mark, operators and governing agents have no visibility into where time was spent—whether during dynamic scenario discovery in `dataForge`, SQLite table schema generation, JSON snapshot serialization, or test harness execution. Without granular phase timestamps and elapsed duration telemetry, pinpointing the true bottleneck requires speculative manual debugging.
4. **Fragility Under Orchestration Constraints**: Prior attempts to bypass timeout issues relied on ad-hoc environment variable overrides (such as `AGENT_ORCH_CODEX_TIMEOUT_SECONDS=3600`) or manual playbook patching. These workarounds do not solve the root architectural vulnerability: workflows must be resilient by design through modular step deconstruction and explicit bottleneck observability, while strictly preserving core DashForge features, snapshot contracts, fail-closed error handling, and backwards compatibility.

## Constraints

The design, implementation, and verification of the `repair-timeout-cascade` slice are strictly governed by the following technical, architectural, and operational constraints:

1. **Core Product Behavior Preservation**: The changes must safely identify bottlenecks in governed runs without altering core product behavior or breaking existing workflows. All existing CLI interfaces (`env PYTHONPATH=src python3 -m dashForge.main generate`), options (`--pack`, `--scenario`, `--seed`, `--output`, `--snapshot-output`, `--force`), and default stdout outputs must remain completely backward compatible.
2. **Canonical Snapshot Contract Integrity**: Diagnostic logging and step deconstruction must not alter the canonical `SQLiteSnapshot` TypeScript contract defined in `frontend/src/core/data/sqliteSnapshot.ts`. Exported JSON snapshots and SQLite databases must remain bit-for-bit deterministic given identical seeds, retaining all seven canonical datasets, complete provenance metadata (`packId`, `scenarioId`, `seed`, `dataForgeStoryContractPath`, generator version, ISO-8601 timestamp, `synthetic: true`, disclosure text `"Synthetic demo data"`), and recommendation queue governance.
3. **Clean Stream Separation & Diagnostic Non-Interference**: Diagnostic timing telemetry and phase logs must not pollute standard output (stdout) or corrupt downstream piping and automated JSON parsing. Diagnostic logs must be routed to standard error (stderr) or dedicated diagnostic handlers, maintaining a clean boundary between operational telemetry and primary payload data.
4. **Fail-Closed Robustness & Clean Error Handling**: Adding timing instrumentation or stage checkpoints must never bypass fail-closed security and validation policies. Existing output files without `--force`, missing required parameters, or invalid scenario IDs must fail closed with exit status 2 and clear diagnostic messages, eliminating raw Python tracebacks.
5. **Zero External Runtime Dependencies**: All diagnostic logging, timing instrumentation, and CLI enhancements must use Python standard library modules only (`time`, `logging`, `argparse`, `json`, `sqlite3`, `pathlib`, `sys`, `dataclasses`). No third-party profiling, APM, or logging packages may be added to runtime requirements.
6. **Read-Only Sibling Boundary**: Sibling repository `dataForge/` is strictly read-only. No files within `dataForge/` may be created, edited, or deleted. All timing and discovery adaptations must be implemented cleanly within DashForge.
7. **Governed Step Timeout Compliance**: All deconstructed playbook steps must be scoped and structured to complete reliably within a fraction of the 600-second threshold (target duration < 120 seconds under normal conditions), ensuring that transient slowdowns do not trigger timeout retries.
8. **Governed Write Scope**: For this contract definition step, persistent writes are strictly restricted to `docs/` and `journeys/`. Touching any file outside these declared paths constitutes an immediate step failure under Agent-Orch rules.

## Validation

Verification of the `repair-timeout-cascade` slice follows a multi-tier automated validation strategy:

1. **Full Automated Test Suite Execution**: Running the complete test suite via `python3 -m pytest tests/ -q` with NO PYTHONPATH override (the orchestrator re-executes claims in a bounded environment whose own PYTHONPATH makes pytest importable, and an override hides it). All tests across existing test files must pass with zero failures.
2. **Timing Telemetry and Bottleneck Identification Verification**: Targeted automated verification confirming that diagnostic timing logs capture execution durations across major pipeline phases (CLI initialization, scenario resolution, SQLite generation, snapshot extraction, and file persistence) with millisecond-level precision.
3. **Stream Separation and Stdout Purity**: Automated checks asserting that diagnostic logs and telemetry messages are emitted to stderr or isolated handlers, leaving stdout clean, uncorrupted, and parseable for downstream consumers.
4. **Deterministic Snapshot and Output Reproducibility**: Automated comparison of generated SQLite databases and JSON snapshots across identical seeds, confirming identical file hashes, column definitions, record counts, provenance metadata, and recommendation queue governance.
5. **Fail-Closed Argument and Overwrite Validation**: Verification that missing arguments, invalid scenario identifiers, or existing output paths without `--force` continue to exit cleanly with status code 2 and helpful diagnostics without raising unhandled Python exceptions.
6. **User Journey Simulation Gate**: Verifying that all user journeys defined in `journeys/user_journeys_manifest.json` execute successfully from the workspace root using allowlisted command strings matching declared exit codes.

## Acceptance Checks

The slice must satisfy the following explicit acceptance checks:

- **AC-1**: Governed workflow playbooks and long-running execution steps subject to the 600-second timeout cascade are deconstructed into modular, bounded stages with explicit inputs, outputs, and intermediate checkpoints; each deconstructed step is scoped to finish well within the 600-second budget, preventing timeout aborts and eliminating cascading whole-workflow retries.
- **AC-2**: The DashForge generation and packaging runtime incorporates structured, low-overhead diagnostic logging and elapsed timing instrumentation that records timestamped durations for major execution phases (CLI initialization, scenario resolution, relational data generation, SQLite table creation, snapshot serialization, and disk persistence) to safely identify performance bottlenecks in governed runs.
- **AC-3**: The CLI entrypoint (`env PYTHONPATH=src python3 -m dashForge.main generate`) safely supports diagnostic logging and telemetry without altering default output formatting or corrupting stdout; diagnostic messages are cleanly separated to stderr or designated diagnostic channels, ensuring downstream scripting and automation pipelines receive unpolluted payload streams.
- **AC-4**: Diagnostic logging and modularized stage execution preserve bit-for-bit generation determinism and schema fidelity; generated SQLite databases and JSON snapshots remain byte-for-byte identical given identical seeds and conform strictly to the canonical `SQLiteSnapshot` contract (`frontend/src/core/data/sqliteSnapshot.ts`), preserving all seven scenario datasets, provenance metadata, and recommendation queue governance.
- **AC-5**: Diagnostic instrumentation and timing utilities fail closed and introduce no unhandled exceptions or raw Python tracebacks; invalid CLI invocations, missing arguments, unknown scenarios, or existing target files without `--force` continue to exit cleanly with status code 2 and informative diagnostic messages.
- **AC-6**: Diagnostic logging and stage deconstruction preserve all existing runtime presentation seams and catalog bindings; the shared `DataAdapter` query routing, `DashboardSpec` contracts, scenario catalog registrations (`snowflakeCost:idle-warehouse-waste`), and template definitions (`tpl.snowflakeCost.idle-warehouse-waste`) remain fully functional without secondary rendering paths.
- **AC-7**: All diagnostic logging and timing facilities rely exclusively on Python standard library modules (`time`, `logging`, `argparse`, `json`, `sqlite3`, `pathlib`, `sys`); sibling repository `dataForge/` remains strictly read-only; all existing packs (`healthcare`, `financial`, `saas`, `snowflakeCost`) remain operational; and the full automated test suite passes cleanly via `python3 -m pytest tests/ -q` with NO PYTHONPATH override.
